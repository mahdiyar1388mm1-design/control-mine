# مرکز کنترل مدیریت (Admin Console)

نسخهٔ جدید بخش مدیریت، یک مرکز کنترل یکپارچه، راست‌چین، کاملاً واکنش‌گرا (Responsive) و هم‌راستا با تم سفید–صورتی برند است. تمام صفحه‌ها در مسیر `/staff` و برای نقش `admin` نمایش داده می‌شوند و هر عملیات حساس در دفتر ممیزی فقط‌افزودنی ثبت می‌شود.

---

## ۱) بخش‌های مرکز کنترل

| بخش | کارکرد |
|---|---|
| **داشبورد** | شاخص‌های زندهٔ کاربران، فرم‌های تکمیل‌شده، درآمد ۳۰ روز، موجودی خزانه، سفارش‌ها، موجودی کالا، تیکت‌ها و درخواست‌های خدمت. نمودار فروش ۱۴ روز، پرفروش‌ترین کالاها، کم‌موجودها و آخرین افراد/سفارش‌ها. بروزرسانی خودکار هر ۴۵ ثانیه. |
| **محصولات** | افزودن محصول در یک مرحله (نام، توضیح، دسته، برند، وضعیت، قیمت فروش/خرید، موجودی، ویژگی و تصاویر)، ساخت دسته و برند جدید (همراه با لوگو) از همان فرم، ویرایش کالا، مدیریت تنوع‌ها (SKU)، تنظیم قیمت‌ها و موجودی، آپلود تصویر و بایگانی/حذف. |
| **برندها** | مدیریت کامل برندها: ساخت برند با **لوگو**، توضیح کوتاه، وب‌سایت، ترتیب نمایش و فعال/غیرفعال‌سازی؛ تعویض یا حذف لوگو مستقیم از کارت برند؛ نمایش تعداد کالاهای هر برند؛ حذف ایمن (برند دارای کالا غیرفعال می‌شود، نه حذف). |
| **کاربران** | دفتر کامل افراد با **شمارهٔ موبایل کامل**، **نام کاربری**، ایمیل، نقش، وضعیت، تعداد نشانی/سفارش/خدمت/تیکت، مجموع خرید و آخرین فعالیت. پروندهٔ کامل هر شخص شامل همهٔ فرم‌های تکمیل‌شده، پرداخت‌ها، دارایی LTH و تایم‌لاین فعالیت. جست‌وجو، فیلتر بر اساس نقش و منبع فرم، ویرایش نام/نام کاربری/ایمیل و تغییر نقش/وضعیت با تأیید مجدد رمز مدیر. خروجی CSV. |
| **سفارش‌ها** | فهرست و جست‌وجوی سفارش‌ها، مشاهدهٔ کامل مشتری، نشانی، اقلام، جمع‌ها، تاریخچه و تغییر وضعیت مجاز. |
| **خزانه** | موجودی ریالی خزانه، ورود/خروج امروز، جریان ۳۰ روز، ترکیب درآمد بر اساس منبع، دفتر تراکنش‌ها و ثبت دستی ورود/تسویه با علت. خزانهٔ پروتکل LTH نیز در همین بخش خلاصه و قابل ورود به مدیریت کامل است. |
| **LTH** | همان پنل کامل پروتکل، خزانهٔ ۱۵٬۰۰۰٬۰۰۰ LTH، ریگلاژ استیک/پایه، کارمزد، بازرسی ۳۶۰ درجه و لوگو. |
| **تنظیمات** | نام فروشگاه، هزینهٔ ثابت ارسال و سقف ارسال رایگان (با ثبت علت در ممیزی). |
| **ممیزی** | دفتر فقط‌افزودنی عملیات حساس با فیلتر و صفحه‌بندی. |

## ۲) تغییرات پایگاه داده — مهاجرت `007_admin_console`

### الف) نام کاربری یکتا

- ستون `users.username` با ایندکس یکتا.
- برای حساب‌های موجود به‌صورت خودکار از شمارهٔ موبایل ساخته می‌شود: `09121234567` ← `cm9121234567`.
- تریگر `trg_users_auto_username` برای هر حساب جدید بدون نام کاربری، نام یکتا می‌سازد.
- ثبت‌نام از API نیز نام کاربری یکتا می‌سازد و در صورت تکرار، پسوند عددی اضافه می‌کند.

### ب) دفتر افراد `people_directory`

جدولی که هر شخص را با اولین و آخرین فعالیت نگه می‌دارد. این جدول **به‌صورت خودکار** توسط تریگرها به‌روز می‌شود:

| رخداد | منبع ثبت‌شده |
|---|---|
| ساخت حساب | `signup` |
| ذخیرهٔ فرم نشانی/ارسال | `shipping_form` |
| ثبت سفارش کالا | `order` |
| ثبت درخواست خدمت | `service_form` |
| ثبت تیکت پشتیبانی | `support_ticket` |

ستون‌ها: `phone`, `username`, `full_name`, `email`, پرچم‌های `has_*`، شمارنده‌ها، `last_source`, `first_seen_at`, `last_seen_at`.
شمارنده‌های دقیق در API از جداول اصلی محاسبه می‌شوند تا حذف/ویرایش هم منعکس شود.

### ج) خزانهٔ ریالی `treasury_cash_ledger`

دفتر ورود/خروج وجه با انواع `product_sale`, `service_sale`, `lth_sale`, `refund`, `payout`, `adjustment`, `opening`.

- تریگر `trg_cash_payment_paid_insert` و `trg_cash_payment_paid_update`: هر پرداخت تسویه‌شده (کالا، خدمت یا LTH) به‌صورت خودکار به‌عنوان ورود ثبت می‌شود.
- تریگر `trg_cash_refund_insert`: هر استرداد به‌صورت خودکار خروج ثبت می‌شود.
- داده‌های تاریخی نیز در همان مهاجرت به‌صورت idempotent پر می‌شوند.
- تنظیمات `treasury_opening_balance_toman` و `treasury_low_balance_toman` به `settings` اضافه شده‌اند.

> مهاجرت برگشتی: `server/src/db/migrations/007_admin_console.down.sql`

### د) برندها و لوگو — مهاجرت `011_brand_logos`

جدول `brands` گسترش می‌یابد تا برند یک رکورد واقعی کاتالوگ باشد:

| ستون | نوع | توضیح |
|---|---|---|
| `logo_path` | TEXT | مسیر لوگو داخل `/uploads/` (مثلاً `brand-logo-<uuid>.png`) |
| `description` | TEXT NOT NULL DEFAULT '' | توضیح کوتاه برند برای فروشگاه |
| `website_url` | TEXT | وب‌سایت اختیاری |
| `is_active` | INTEGER NOT NULL DEFAULT 1 | `0` = پنهان از فروشگاه (کالاها دست‌نخورده می‌مانند) |
| `sort_order` | INTEGER NOT NULL DEFAULT 0 | ترتیب نمایش فیلتر برند |
| `created_at` / `updated_at` | TEXT | زمان ثبت و آخرین ویرایش |

- ایندکس `idx_brands_active_sort` برای فهرست مرتب فروشگاه.
- تنظیم `brand_logo_max_bytes` به `settings` اضافه می‌شود.
- محصولات همان `products.brand_id` قبلی را دارند؛ **هیچ تغییری در جدول محصولات لازم نبود**.
- مهاجرت برگشتی: `server/src/db/migrations/011_brand_logos.down.sql` (ابتدا ایندکس، بعد ستون‌ها).

#### قواعد امنیتی لوگو

1. فقط `image/png`، `image/jpeg` و `image/webp` پذیرفته می‌شود (پسوند + MIME اعلامی + **امضای واقعی بایت‌ها**).
2. نام فایل همیشه سمت سرور ساخته می‌شود (`brand-logo-<uuid>.ext`)؛ نام کاربر هرگز استفاده نمی‌شود.
3. SVG رد می‌شود (بردار ذخیره‌شدهٔ XSS).
4. مسیر ذخیره‌شده فقط با الگوی `/uploads/...` پذیرفته می‌شود، پس مقدار دلخواه از API قابل تزریق نیست.
5. با تعویض یا حذف لوگو، **فایل قبلی از دیسک پاک می‌شود**؛ با حذف برند بی‌کالا نیز لوگو حذف می‌گردد تا فایل یتیم نماند.
6. آپلود از مسیر `POST /admin/brands/:id/logo` انجام می‌شود، پس همان سد CSRF و ممیزی بقیهٔ نوشتن‌ها را دارد.

## ۳) قرارداد API

همهٔ مسیرها زیر `/api/v1/admin/console` و فقط برای نقش `admin`:

| متد | مسیر | توضیح |
|---|---|---|
| GET | `/overview` | شاخص‌های زنده، نمودار ۱۴ روزه، آخرین افراد/سفارش‌ها، کم‌موجودها، پرفروش‌ها |
| GET | `/people` | دفتر افراد با شمارهٔ کامل + نام کاربری؛ فیلتر `q`, `role`, `status`, `source`, `with_activity` |
| GET | `/people.csv` | خروجی CSV (حداکثر ۵۰۰۰ ردیف) |
| GET | `/people/:id` | پروندهٔ کامل: نشانی‌ها، سفارش‌ها، خدمات، تیکت‌ها، پرداخت‌ها، LTH، تایم‌لاین |
| PATCH | `/people/:id` | ویرایش نام/نام کاربری/ایمیل؛ تغییر نقش/وضعیت نیازمند `reason` و `current_password` مدیر |
| GET | `/products` | کالاها با قیمت حداقل/حداکثر، موجودی، تعداد تنوع و تصویر |
| POST | `/products` | ایجاد یک‌مرحله‌ای کالا + SKU اول + دسته/برند جدید اختیاری |
| POST | `/products/:id/archive` | حذف یا بایگانی بر اساس سابقهٔ سفارش |
| GET | `/brands` | فهرست برندها (همراه برندهای غیرفعال) + تعداد کالا |
| POST | `/brands` | ساخت برند با توضیح، وب‌سایت، ترتیب و وضعیت |
| PATCH | `/brands/:id` | ویرایش برند؛ تغییر نام، اسلاگ یکتا را خودکار بازسازی می‌کند |
| DELETE | `/brands/:id` | حذف برند بی‌کالا؛ برند دارای کالا فقط غیرفعال می‌شود |
| DELETE | `/brands/:id/logo` | حذف لوگو و پاک‌سازی فایل از دیسک |
| GET | `/orders` | فهرست سفارش‌ها با شماره و نام کاربری مشتری |
| GET | `/orders/:code` | جزئیات کامل سفارش |
| GET | `/treasury` | خلاصه، روند ۳۰ روز، ترکیب درآمد، دفتر تراکنش‌ها و خزانهٔ LTH |
| POST | `/treasury/adjust` | ثبت دستی ورود/خروج با علت (ممیزی‌شده) |
| PATCH | `/treasury/settings` | موجودی افتتاحیه و حد هشدار |

مسیرهای موجود قبلی (مدیریت کالا، SKU، تنظیمات، گزارش‌ها و ممیزی) بدون تغییر باقی مانده‌اند و کنسول از همان‌ها استفاده می‌کند.

### مسیرهای آپلود و مدیریت عمومی برند (در ماژول کاتالوگ)

| متد | مسیر | دسترسی | توضیح |
|---|---|---|---|
| GET | `/brands` | عمومی | فقط برندهای فعال، مرتب بر اساس `sort_order` |
| GET | `/brands/:slug` | عمومی | جزئیات یک برند فعال |
| GET | `/admin/brands` | `admin`, `warehouse` | فهرست کامل با شمارش کالا |
| POST | `/admin/brands/:id/logo` | `admin` | آپلود لوگو با فیلد `logo` (multipart) |
| PATCH | `/admin/brands-order` | `admin` | ترتیب‌دهی گروهی برندها |

## ۴) امنیت و شفافیت

- کل مسیر کنسول با `requireRole('admin')` محافظت می‌شود؛ مشتری و سایر کارکنان خطای `403` می‌گیرند.
- نمایش شمارهٔ کامل و پروندهٔ کاربر در ممیزی ثبت می‌شود (`admin.view_person_profile`, `admin.export_people`).
- تغییر نقش/وضعیت حساب همچنان نیازمند علت و تأیید مجدد رمز عبور مدیر است و حداقل یک مدیر فعال را تضمین می‌کند.
- شماره کارت/شبا در پرونده فقط با چهار رقم آخر نمایش داده می‌شود.
- تمام تغییرهای خزانه و تنظیمات با علت در `audit_log` ثبت می‌شوند.

## ۷) کلیدهای حسابداری پروتکل در کنسول مدیریت LTH

در تب **خزانه پروتکل** پنل مدیریت (`/staff` → مدیریت سامانه → LTH) دو کارت تازه اضافه شده است:

### الف) ردیف‌های خزانه (مرتب و با آیکن)
هر ردیف با آیکن SVG و راهنمای کوتاه نمایش داده می‌شود؛ ستون عدد همیشه `LTR` و
با ۱۲ رقم اعشار است. ردیف «میزان پایه» مقدار `issue_base − return_base` است و
اگر کیف پول قدیمی پایه‌ای خارج از ردیابی داشته باشد، در `opening_atoms` گزارش می‌شود.

| ردیف | معنا |
|---|---|
| میزان پایه | پایهٔ صادرشده منهای پایهٔ بازگشتی |
| جمع بازگشت استیک / پایه / پاداش | بازگشت‌های سه‌گانه به خزانه |
| جمع کارمزد | همهٔ `collect_fee`ها |
| مالیات تعلق‌گرفته / پرداخت‌شده / ماندهٔ مالیات | چرخهٔ مالیات روی کارمزد |
| کارمزد خالص | کارمزد پس از کسر مالیات |

### ب) کارت «مالیات روی کارمزدهای دریافتی»
- سه KPI: تعلق‌گرفته، تسویه‌شده، مانده (ماندهٔ مثبت قرمز می‌شود).
- **مدیر کل:** فرم ثبت نرخ (`PATCH /admin/lth/tax`) و فرم تسویه
  (`POST /admin/lth/tax/settle` با مبلغ، مرجع پرداخت و علت).
- **کارشناس مالی:** فقط مشاهده؛ فرم‌ها رندر نمی‌شوند.
- تسویهٔ بیش از مانده → خطای `409` با پیام فارسی و بدون تغییر داده.

### ج) کارت «پاداش کل بازار و ستون مهندسی معکوس»
جدول دو دسته سناریو دارد: **بازار فعلی** و **کل عرضه**، هر کدام برای ۷۰/۳۰ (ریگلاژ
زنده) — و اگر اپراتور سهم استیک دیگری بدهد، همان هم به‌عنوان سناریو اضافه می‌شود.
ستون «میزان بازار»، «پاداش ۲۴ساعته» و «ارزش ریالی» است، یعنی با داشتن عدد پایه
می‌توان میزان ارز فروخته‌شده/بازار را مهندسی معکوس کرد:

```
required_market = (target_reward × 10^8) ÷ reward_per_min_unit
```

فرم پایین کارت سهم استیک و «پاداش هدف» را می‌گیرد و سهم بازار از عرضه را
(`market_share_of_supply_percent`) همراه با «در سقف عرضه ممکن است / نیست» برمی‌گرداند.

## ۸) قواعد UI که نباید بشکنند
- هیچ ایموجی‌ای در سایت رندر نمی‌شود: `installEmojiScrubber()` در `main.jsx` گره‌های
  متنی ایموجی را حذف می‌کند، پس هر آیکن باید `<Icon name="..." />` از
  `client/src/components/Icon.jsx` باشد (رِجیستری ۹۰ آیکن SVG خطی صورتی).
  برای موارد استثنایی `data-keep-emoji` وجود دارد ولی عملاً نباید استفاده شود.
- آیکن‌های حساب کاربری، تب‌های میزکار کارکنان، ردیف‌های خزانه و همهٔ هدرهای پنل با
  `<Icon>` رندر می‌شوند؛ تست jsdom روی API زنده: **۰ ایموجی، ۰ آیکن خالی، ۰ خطای کنسول**.
