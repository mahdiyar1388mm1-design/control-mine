# فاز صفر — کشف نیازها: CENTRAL MINE

> وضعیت: طراحی‌شده (این سند). کدنویسی پس از این سند آغاز شده است.
> تاریخ: 2026-11-11

## ۱. خلاصهٔ محصول و محدودهٔ نسخهٔ اول

**CENTRAL MINE** یک پلتفرم فارسی (راست‌چین، موبایل‌محور) با دو فعالیت اصلی است:

1. **فروشگاه آنلاین کالای فیزیکی:** کاتالوگ، دسته‌بندی، برند، جست‌وجو و فیلتر مبتنی بر سرور، صفحهٔ جزئیات با تنوع SKU، سبد خرید، ثبت سفارش، پرداخت، رسید، پیگیری سفارش، ارسال و مرجوعی.
2. **سامانهٔ خدمات عملیاتی:** تعریف خدمت با فرم نسخه‌دار، ثبت درخواست مشتری با کد پیگیری، صف و پنل اپراتور، گفتگوی پرونده، درخواست اطلاعات تکمیلی، تحویل نتیجه/فایل، کنترل SLA، پرداخت خدمت.

زیرساخت مشترک: حساب کاربری و احراز هویت، پروفایل و نشانی، تیکت پشتیبانی، اعلان درون‌سامانه‌ای، پنل‌های نقش‌محور کارکنان و مدیریت، گزارش‌های پایه، ممیزی عملیات حساس، مستندات اجرا و آزمون.

**خارج از محدودهٔ نسخهٔ اول (عمداً):** کیف پول، توکن، استیکینگ، خریدوفروش دارایی، هرگونه عملیات مالی پیچیده، اتصال واقعی درگاه پرداخت، اتصال واقعی پیامک، اعلان Push. این موارد فقط با تأیید کارفرما (قوانین، نرخ‌ها، کارمزدها، سناریوهای شکست) وارد فازهای بعد می‌شوند و در این نسخه «فعال» جلوه داده نمی‌شوند.

## ۲. کاربران و نقش‌های سازمانی

| نقش | هدف | مجاز | ممنوع (نمونه) |
|---|---|---|---|
| بازدیدکننده | مشاهدهٔ عمومی | دیدن کالا/خدمات فعال، جست‌وجو | دیدن دادهٔ خصوصی، ثبت سفارش بدون ورود |
| مشتری | خرید و پیگیری | حساب/نشانی، سبد، سفارش، درخواست خدمت، پیام پرونده، تیکت، اعلان | دیدن پرونده/سفارش دیگران، یادداشت داخلی |
| اپراتور خدمات | انجام درخواست‌ها | صف مجاز، تخصیص، پیام، تغییر وضعیت طبق گردش‌کار، نتیجه/فایل | رد کردن پیش‌نیاز وضعیت، دیدن دادهٔ مالی نامرتبط |
| کارشناس پشتیبانی | تیکت‌ها | پاسخ، ارجاع، وضعیت تیکت | تغییر پرداخت/موجودی بدون مجوز |
| مسئول انبار و ارسال | پردازش سفارش | آماده‌سازی، ارسال، شمارهٔ رهگیری، اصلاح موجودی با دلیل | دسترسی مالی/حساب کاربران |
| مسئول مالی | پرداخت و استرداد | مشاهده، استرداد با مرجع/علت/ممیزی | — |
| مدیر | مدیریت سامانه | کاربران/نقش‌ها، کالا، خدمت، تنظیمات، گزارش، ممیزی | دسترسی بی‌قیدوشرط بدون ثبت ممیزی |

همهٔ مجوزها **سمت سرور** بررسی می‌شوند؛ مالکیت رکورد برای هر دادهٔ مشتری کنترل می‌شود. پنهان‌کردن دکمه در فرانت‌اند کنترل دسترسی نیست.

## ۳. جریان‌های اصلی

### مشتری — فروشگاه
بازدید/جست‌وجو → صفحهٔ کالا → انتخاب SKU → سبد → ورود/ثبت‌نام → انتخاب نشانی → بازبینی قیمت و موجودی **در سرور** → ثبت سفارش (idempotent) → پرداخت sandbox → رسید → پیگیری وضعیت → تحویل/تکمیل (یا لغو/مرجوعی طبق قاعده).

### مشتری — خدمات
فهرست خدمات → مطالعهٔ شرایط → تکمیل فرم + بارگذاری مدارک → خلاصه و هزینه → ثبت و دریافت کد پیگیری → (در صورت نیاز) پرداخت → پیگیری وضعیت → پاسخ به درخواست اطلاعات تکمیلی → دریافت نتیجه/فایل.

### اپراتور خدمات
صف (فیلتر بر اساس خدمت/وضعیت/فوریت/SLA) → تخصیص به خود/همکار → بررسی مدارک → پیام/درخواست اطلاعات → تغییر وضعیت طبق گردش‌کار → ثبت نتیجه یا فایل خروجی → تکمیل. یادداشت داخلی فقط برای کارکنان.

### پشتیبانی
تیکت مشتری (کد پیگیری) → پاسخ کارشناس → ارجاع/وضعیت → حل‌شده/بسته. تیکت از درخواست خدمت جداست.

### انبار/ارسال
سفارش «پرداخت‌شده» → آماده‌سازی → ارسال (ثبت شمارهٔ رهگیری، نمایش برای مشتری فقط پس از ارسال) → تکمیل.

### مالی
مشاهدهٔ پرداخت‌ها → رسید از دادهٔ سرور → استرداد با مرجع و علت و ثبت ممیزی.

## ۴. مدل مفهومی داده و مرز ماژول‌ها

هر ماژول مالک داده و مسئولیت خود است (کنترلر بزرگ متمرکز نداریم):

- **identity:** کاربر، نشانی، نشست قابل ابطال، OTP، تغییر رمز
- **catalog:** دسته، برند، محصول، تصویر، SKU، حرکت موجودی
- **cart:** سبد و اقلام (قیمت/موجودی قطعی در سرور محاسبه می‌شود)
- **orders:** سفارش، اقلام (اسنپ‌شات قیمت و قیمت خرید برای سود)، تاریخچهٔ وضعیت
- **payments:** پرداخت مستقل از سفارش، رویداد callback (idempotent)، استرداد
- **services:** تعریف خدمت، نسخهٔ فرم/شرایط، درخواست، گفتگو، فایل، گردش‌کار و SLA
- **support:** تیکت، پیام، پیوست
- **platform:** اعلان، ممیزی، فایل خصوصی، کلید idempotency، تنظیمات

ارتباط‌ها: Order ↔ Payment، ServiceRequest ↔ Payment، همه ↔ User. جزئیات کامل در `02-data-model.md`.

## ۵. نقشهٔ صفحات

**عمومی:** خانه، فهرست کالاها (جست‌وجو/فیلتر/صفحه‌بندی)، جزئیات کالا، فهرست خدمات، جزئیات خدمت و فرم درخواست، ورود/ثبت‌نام، پیگیری درخواست با کد.

**حساب مشتری:** سبد، تسویه، پرداخت و رسید، سفارش‌های من + جزئیات و تاریخچه، درخواست‌های خدمات من + جزئیات (پیام/فایل)، تیکت‌ها، اعلان‌ها، پروفایل و نشانی‌ها.

**کارکنان (نقش‌محور):** پنل اپراتور (صف + فضای کار پرونده)، پشتیبانی (صندوق تیکت)، انبار (آماده‌سازی/ارسال)، مالی (پرداخت/استرداد)، مدیر (داشبورد گزارش، کالا، خدمت، کاربران، تنظیمات، ممیزی).

**فهرست APIها:** `03-api.md`

## ۶. ابهام‌ها، فرض‌های کم‌خطر، و پرسش‌های دسته‌بندی‌شده

### فرض‌های کم‌خطر اعلام‌شده (قابل تغییر با پاسخ کارفرما)
1. **واحد پول: تومان**، مقادیر صحیح؛ همه‌جا برچسب «تومان» کنار مبلغ.
2. **ورود:** موبایل + رمز عبور + مسیر OTP آزمایشی (کد در محیط توسعه در کنسول/پاسخ dev چاپ می‌شود — به پیامک واقعی متصل **نیست**).
3. **پرداخت:** فقط adapter آزمایشی (sandbox) با صفحهٔ درگاه شبیه‌سازی‌شده و callback امضاشده؛ «فعال» اعلام نشده برای تولید.
4. **ارسال:** نرخ ثابت + رایگان بالای مبلغ آستانه (در تنظیمات قابل تغییر).
5. **سیاست موجودی:** کسر هنگام ثبت سفارش در تراکنش؛ آزادسازی هنگام لغو **حداکثر یک‌بار** با ثبت تاریخچه.
6. **حذف کالا:** soft-delete؛ کالای دارای سفارش حذف فیزیکی نمی‌شود.

### پرسش‌های اثرگذار (برای تأیید کارفرما — پاسخ‌ها فاز بعد را شکل می‌دهد)
1. **درگاه پرداخت واقعی:** کدام درگاه (زرین‌پال/ملت/...)؟ credential آزمایشی موجود است؟
2. **کانال پیامک:** ارائه‌دهنده و الگوی پیامک تأیید؟ (فعلاً adapter کنسولی)
3. **واحد پول نهایی:** تومان یا ریال؟ (فعلاً تومان)
4. **قوانین مالیات/ارزش افزوده و فاکتور رسمی:** لازم است؟
5. **سیاست مرجوعی دقیق:** بازهٔ زمانی، شرایط، هزینهٔ بازگشت.
6. **ظرفیت روزانهٔ خدمات واقعی** و تیم‌های عملیاتی.

## ۷. برنامهٔ مرحله‌ای اجرا و معیار پذیرش

| فاز | خروجی | معیار پذیرش |
|---|---|---|
| ۰ کشف | همین سند + اسناد طراحی | بازبینی‌پذیر بودن اسناد |
| ۱ طراحی | معماری، مدل داده، قرارداد API | تثبیت قرارداد پیش از UI |
| ۲ پایهٔ فنی | پروژهٔ تازه، migration، احراز هویت، خطا/لاگ، تست | ورود/خروج/نشست کار می‌کند؛ تست پاس |
| ۳ فروشگاه و سفارش | کاتالوگ، SKU، سبد، سفارش، پرداخت sandbox، رسید | زنجیرهٔ کامل خرید از UI تا DB پس از refresh پایدار |
| ۴ خدمات | تعریف خدمت، فرم نسخه‌دار، درخواست، اپراتور، گفتگو، SLA، نتیجه | گردش‌کار کامل با تاریخچه؛ یادداشت داخلی از API مشتری برنمی‌گردد |
| ۵ پشتیبانی و پنل‌ها | تیکت، پنل نقش‌ها، ممیزی، گزارش‌ها | مالکیت و مجوز سمت سرور؛ گزارش‌ها با منبع/واحد/بازه |
| ۶ کیفیت | تست سناریوهای بخش ۱۸ | نتایج واقعی تست ثبت شود |
| ۷ عملیات | مستندات اجرا/استقرار/backup/rollback | اجرای محلی با یک فرمان |

**اصل پذیرش:** برای هر قابلیت زنجیرهٔ کامل «رابط → API → مجوز/اعتبارسنجی → منطق دامنه → ذخیرهٔ پایدار → پاسخ → نمایش → ماندگاری بعد از refresh» برقرار باشد؛ در غیر این صورت «ناقص» گزارش می‌شود.

## ۸. ریسک‌ها

| ریسک | اثر | کاهش |
|---|---|---|
| فروش بیش از موجودی (سفارش هم‌زمان) | مالی/عملیاتی | قفل تراکنش + شمارش شرطی موجودی + تست هم‌زمانی |
| callback تکراری درگاه | مالی | جدول رویداد + کلید یکتای callback + تراکنش |
| دسترسی مشتری به دادهٔ دیگران | امنیتی | کنترل مالکیت در هر endpoint + تست نفوذ |
| افشای قیمت خرید/یادداشت داخلی | امنیتی | جداسازی schema خروجی نقش‌ها + تست |
| ادعای دروغین قابلیت (پیامک/درگاه واقعی) | اعتماد | برچسب‌گذاری صادقانهٔ sandbox و غیرفعال‌ها |
| ناسازگاری تغییر فرم خدمت با پرونده‌های قدیمی | عملیاتی | اسنپ‌شات نسخهٔ فرم و شرایط در زمان ثبت |
